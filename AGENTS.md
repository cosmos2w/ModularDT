# Repository completion and upload rule

- After a round of code revision, commit the durable changes and push the current non-default working branch. Fetch or inspect the remote branch before pushing, then verify the remote and local branch tips match. A local commit alone does not finish the round.
- Before every push, audit the **entire outgoing commit range**, including files that an earlier outgoing commit added and a later one deleted. Never upload highly one-time diagnostic code, generated figures, or generated data, except the user-approved curated README PNG/PDF assets under `docs/assets/readme/`. Keep those artifacts locally in ignored paths. Do not force-add ignored outputs.
- If forbidden files are already in unpublished commits, rebuild the outgoing history before pushing. Preserve a local backup first, and leave the working checkout synchronized with the pushed branch.
- Run `git config core.hooksPath .githooks` in this clone so the repository pre-push artifact gate runs. Review its result and the outgoing file list; the gate supplements the required human audit.

# HONF architecture and interpretation

- Use `Model_Explain.md` as the canonical notation and terminology for new model mathematics. Bind explanations to an explicit source branch and commit; distinguish global conditions, raw scores, applied contextual gates, prepared directories and final query contributions. Update its local Chinese mirror with the English source when revising their shared content.
- HONF learns relationships that do work during contextual information exchange and are reused to govern query access and distribution. Preserve individual record identity, coordinates, physical measures and prescribed controls. A group describes membership, relations and permitted operations; it is not defined as a pooled feature that must replace its members.
- Organization-controlled access to individual M/E members is a legitimate primary path. It is not a bypass. An additional value path that ignores organization is a bypass. Shared summaries and local calculations are permitted operations, but must not become the only legal information source by default. Do not classify a successful routed member reader as failed organization merely because its predictions need member detail.
- M/E denote input-object roles, not output-physics responsibilities. New HONF models must use a general joint physical-field predictor, with prescribed geometry, materials, boundaries and controls entering their owning objects before interaction. Do not inherit Thermal-specific heat-affine heads, separate flow/temperature prediction paths, heat-independent routing/flow assumptions or analytical correction branches as generic architecture. The same rule applies to future Wind and other cases. Case adapters own units, normalization, physical targets and native observation/extraction; dataset generation shortcuts do not define the shared core. Preserve historical models and their loading behavior without promoting their specializations into new designs.
- Keep actual applied directed relations and their stage provenance clear. Reusing an attention implementation, pooled values or a post-hoc visualization alone does not establish relation reuse. A transposed index is a reverse lookup, not evidence that the reverse exchange actually ran.
- Select eligible groups/members before expensive query-conditioned scores or values when claiming saved work. Report actual selected records, executed pair calculations, preparation/index costs and complete runtime separately. A smaller directory, fewer nonzero weights or lower memory alone does not establish end-to-end savings or physical causality.
- Treat exchange order, E→E, layer count, M-first addressing, overlapping membership and address count as testable choices. Do not impose a forced leaf period, delayed permission to merge, target K, mandatory M/E winner or organization freeze. Explicit finite execution budgets are resource/model settings to measure, not discovered physical group counts.

# Training units, development budget and fair comparison

- Express every training horizon, budget, continuation, progress description and agent handoff in **epochs only**. An epoch visits the declared training membership once. Do not introduce alternative iteration-based units into user-facing explanations or new documentation. Preserve existing raw scientific histories without rewriting them.
- Segmented/subset data is for execution debugging and qualification, not architectural maturity claims. Reuse the fixed input-stratified manifest in `docs/guides/Thermal_Model_Development_Protocol.md`; use only the epochs necessary to verify execution, learning-path health, checkpointing and resume. The total segmented fitting allowance for a new round is at most **500 epochs**, including retries and comparison arms, unless the user explicitly sets another budget. This is a ceiling, not a target or permission to exhaust it.
- Meaningful predictor/organizer conclusions require full-training-population experiments and sufficiently mature trajectories. The default first full-data segment is at most **100 epochs per explicitly selected model**. Save its evidence and resumable state and describe the endpoint as preliminary. For a round's explicitly proposed final formal candidate, the user grants a standing exception: after its completed 100-epoch review, Codex may decide from predictor, organizer and learning-health evidence whether to resume that same lineage to **500 total epochs**. Record the decision and rationale; an imperfect early endpoint is not an automatic rejection. This exception does not authorize extending every control, old A/B run or qualification run, restarting from scratch, exceeding the round's declared budget, or continuing beyond 500 epochs. Other extensions require explicit instruction. Do not promote a short segmented fit into a scientific verdict or treat full-data100 as convergence or architectural failure. A missing code path or incorrect equation can be established directly without waiting for mature training.
- Reuse one input-only membership and case order across compared models. Preserve module-count categories, source train/validation/test separation and train-only normalization; match initialization, query sampling, physical objectives, schedules and epoch/case budgets. Do not select or resample cases from model errors, create new manifest hashes/freezes, or silently cross dataset/normalization identities during resume. Full-data runs are separately named lineages; debugging weights are not silently promoted into them.
- Retain latest state, one best-field alias and declared 100-epoch milestones, plus the requested final or clean-stop checkpoint. Refresh loss curves every 10 epochs and at completion; short qualification also retains an actual initial/final curve when substantive. Do not create 25-epoch snapshots or duplicate selector copies. Statistical validation uses the declared fixed panel; detailed fields/graphs use a small fixed representative panel. Reuse unchanged measured artifacts. Preserve existing mature references and scientific checkpoint retention.

- After any segmented or full-data training launch, delegate read-only monitoring to a **Luna agent**, explicitly selecting the available Luna model with a minimal run-specific handoff rather than inheriting the expensive parent's model/history. Give it the exact owned run, declared epoch stop, log/checkpoint locations and notification condition. Use one startup check to establish real epoch timing and estimate completion; schedule the next meaningful inspection near completion (normally after roughly 80–90% of the estimated remaining duration), or at an already declared necessary milestone. Do not repeatedly inspect logs, GPU state or checkpoints without a concrete failure signal or materially changed estimate.
- Exception for the final formal candidate's authorized 100→500 continuation: verify successful resume/startup once, retain ordinary in-process training logs/curves/checkpoints, and finish the task. Do not attach or retain a Luna monitor, observer, polling loop, completion wait or follow-up automation for that continuation. Report startup as startup, not completion. All initial formal100 and segmented runs still receive the ordinary sparse Luna monitoring above; Luna remains available for other useful subtasks.
- Luna should stay quiet while nothing actionable changes and notify the parent only on completion, failure, meaningful delay or required user action. The parent does other necessary work or rests/waits; it must not duplicate the monitor's polling. Use available completion/wait mechanisms, without creating a new daemon, reservation system, admission layer or monitoring framework. A read-only monitor does not authorize new runs, restarts or extensions.
- Do not add cryptographic hashes, contract freezes, baseline snapshots or blocking gates by default. A proposed exception must identify a concrete failure and prove why ordinary Git history, existing IDs/manifests, types, atomic writes and focused tests are structurally insufficient. Preserve existing security, TEST/data, job-ownership, checkpoint and upload safeguards. New blocking gates belong only at irreversible state changes, cross-system mutations, critical security perimeters or formal production releases. Research comparison bands and heuristic checks are evidence, not new admission services; actual execution and measurements take precedence over assertions.
