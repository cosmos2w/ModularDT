# Repository completion and upload rule

- After a round of code revision, commit the durable changes and push the current non-default working branch. Fetch or inspect the remote branch before pushing, then verify the remote and local branch tips match. A local commit alone does not finish the round.
- Before every push, audit the **entire outgoing commit range**, including files that an earlier outgoing commit added and a later one deleted. Never upload highly one-time diagnostic code, generated figures, or generated data. Keep those artifacts locally in ignored paths. Do not force-add ignored outputs.
- If forbidden files are already in unpublished commits, rebuild the outgoing history before pushing. Preserve a local backup first, and leave the working checkout synchronized with the pushed branch.
- Run `git config core.hooksPath .githooks` in this clone so the repository pre-push artifact gate runs. Review its result and the outgoing file list; the gate supplements the required human audit.

# Storage budget and mandatory round cleanup

- Every round includes storage preparation and cleanup. Do not mark a round complete while generated, unnecessary intermediate data remains merely because it is ignored by Git. Closeout must report files/bytes removed, artifacts retained, and actual remaining filesystem capacity.
- Before materializing data, record current free space, a hard budget for new disk bytes, estimated peak temporary space, and minimum free-space headroom on each affected filesystem. Include caches, dataset copies, checkpoints and evaluation exports. Refuse or reduce materialization that would exceed these limits; use memory-only operation when no persistent-cache budget is recorded. A RAM cache limit is not a disk limit.
- Reuse an existing verified shared cache keyed by exact recipe and input/geometry identity. Do not create separate cache stores for comparison arms, archived/current code, runs or checkpoints when those keys already match. Preserve numerical precision, physical measures and deterministic query draws; saving space does not authorize changing scientific semantics.
- Short replays, qualification and cost checks must use the shared cache or disposable temporary storage. Do not duplicate full datasets or existing geometry catalogues for a small diagnostic. Any necessary round-local cache has a declared owner, byte budget and expiry at round closeout.
- The user's standing cleanup instruction authorizes removal of round-owned disposable caches, duplicated intermediate data, failed temporary outputs and superseded visual exports after retained results/failure evidence are validated. Perform this routine cleanup without asking again. This does not authorize deleting source data, code/scripts, historical or declared scientific checkpoints, active-run artifacts, required physical-reference arrays, provenance/metrics/manifests, or the only copy of reusable shared data. Keep the existing declared checkpoint cadence and selected/latest aliases unless the user explicitly changes retention.
- Before removal, freeze protected roots and create an exact recursive allowlist with sizes, ownership, inode/link information and hashes where duplication matters. Recheck active processes, open handles/mappings, symlinks/hardlinks, downstream readers and report/manifest dependencies. Delete only verified disposable entries; preserve the compact checksum/provenance manifests and a receipt identifying removed payloads. Do not silently rewrite historical evidence to hide cleanup.
- Retain the selected numerical evidence needed for metrics, figures and scientific interpretation. At closeout, verify retained files/checkpoints and unrelated jobs are unchanged, verify the allowlisted payloads are absent, and record before/after free space. Keep cleanup manifests, receipts and one-time cleanup helpers locally in ignored paths; upload durable policy/code/tests/docs only under the repository completion rule above.

# Report source formatting (strict)

- Write every prose paragraph in every report on a single continuous source line. Never hard-wrap report text to a fixed column width; use the editor or renderer's visual wrapping instead.
- Preserve blank lines between paragraphs and the required structure of headings, lists, tables, fenced code, display math, and figure embeds. Figure captions are prose paragraphs and must also remain on one source line.
- When revising or formatting a report, preserve this rule and check that no prose paragraph contains inserted line breaks. Configure any formatter used on reports to preserve unwrapped prose.

# Scientific experiment reporting

- Begin final experiment reports with a plain-language account of what changed, then state gains, misses, measured evidence, and next steps separately for predictor, organizer, and inverse results. Distinguish completed measurements from startup checks, surrogate checks, and untested claims.
- Include readable, visually inspected figures from saved numerical evidence for physical fields and residuals, actual interaction graphs/support, fidelity versus work, responses, and inverse designs or sample trails. Label data source, partition, checkpoint, units, controls, failures, and physical-reference limits. Keep generated figures and one-time renderers in ignored local paths under the upload rule above.
- Retain only the most important result figures and remove superseded or redundant generated visual exports after validating the selected figures. Keep PDF as the default retained format; keep a small raster companion only when direct Markdown embedding is specifically required. Make the key figures easy to find in one short index.
- Embed the selected figures directly in the Markdown report when the display format supports it. Immediately after each figure, give its quantitative description and a concise summary of what the measurement supports or misses. Check every local figure link; do not add generated figures to Git.
- State whether sparse work and executor savings were actually measured; report full-access fallback separately. Do not interpret learned support as physical causality or sampler diversity as valid designs.

# Model development budget and fair comparison

- The default for future Thermal model development is the fixed stratified quarter-data protocol in `HONF_Proj/docs/guides/Thermal_Model_Development_Protocol.md`. Use its development profiles and reproducible subset manifest. Full-dataset training/evaluation is reserved for an explicitly requested formal run or final validation.
- Freeze one input-only sampled train/validation selection before comparing models. Preserve all available module-count categories, source train/test separation and normalization fitted only on the selected training cases. Reuse identical IDs, manifest fingerprint, initialization seed, query sampling, losses, schedule and case/update budgets across compared models; never resample validation or select cases from model errors.
- A development epoch visits every selected case, not the complete source dataset. Report actual case visits, optimizer updates, queries and elapsed time. Development metrics are exposed validation evidence; do not relabel them as full-population or independent-test results or compare them fairly with differently trained baselines without stating the difference.
- For a 1,000-epoch development horizon, save monitoring checkpoints, latest state, best-field state and plots every 100 epochs, plus an explicitly requested final stop. Keep only the best-field alias, latest alias and declared milestones. Do not create intermediate 25-epoch snapshots or duplicate selector copies. Evaluate best-field selection over saved monitoring checkpoints consistently for every model.
- Review at 100 epochs before extending to 500; extension to 1,000 needs evidence and an explicit budget. Do not automatically launch a portfolio, expand evaluation to all source cases, or start long formal runs. Compute statistical development metrics on the fixed quarter validation panel; save detailed physical fields/graphs for only a small fixed representative panel. Reuse existing measured artifacts when a checkpoint and protocol have not changed.
- Development and formal dataset identities are distinct. Reject silent resume or comparison across different memberships, normalization bases or schedules. Formal full-data training is a separately labelled run of the chosen architecture, with its own dataset binding and lineage. Keep mature references and existing scientific checkpoints intact; do not mass-delete historical runs as part of changing future policy.
