# HONF Project

`HONF_Proj` is the maintained implementation of the Hypergraph Organized Neural Field (HONF): a continuous neural operator for fields generated by a variable-size set of interacting physical modules. The repository contains a case-neutral forward core, inverse-design models, strict configuration and run services, and the complete ThermalChannel application with a frozen local thermal-disk surrogate.

The current scientific forward baseline is Run 1401 best-by-field at epoch 4585. Its architecture is deliberately direct:

- fixed $K=6$ hyperedges;
- softmax module, environment, and query assignments;
- raw organizer hyperedge state (`use_hyper_mechanism_encoder=false`);
- enhanced hypergraph-gated pairwise decoding;
- dense context fusion for $[u,v,p,\omega,T]$;
- frozen Stage-A local surrogate with one physical interaction refinement.

The profile registry recommends `src/config_core/forward/stage7_structured_context.json` as the historical/scientific Run-1401 architecture profile. The behavior-equivalent `src/config_core/forward/experiments/stage7_fused_query_module.json` overlay is the promoted efficient K=6 training/evaluation execution path; dense full-beta training remains exact, and sparse beta-0.98 gathering is only an evaluation-time override. Run 1000 remains the historical golden compatibility reference. Run 1600's factorized R96 kernel was rejected at epoch 500. The K-scaling audit is complete: Run 1601 is the fused K=6 execution control, Run 1602 is a completed but non-promoted K=4 research reference, and Run 1603 K=8 was rejected at epoch 500. Run 1401 remains the scientific baseline.

Stage-1–6 exchangeable, adaptive, entmax, additive, and gathered modes remain loadable for compatibility and research, but they are not the default scientific platform.

## 1. Quick start

Run commands from `HONF_Proj` in the `ModularDT` environment.

```bash
conda activate ModularDT
python -m pip install -e . -e ./Case_ThermalChannel
```

Validate the current profile, dataset, configured Stage-A checkpoint, device,
and output path without creating a run:

```bash
python train.py \
  --config src/config_core/forward/stage7_structured_context.json \
  --experiment-overlay src/config_core/forward/experiments/stage7_fused_query_module.json \
  --run-id 1500 \
  --device cuda:0 \
  --dry-run
```

Replace `1500` with an unused numeric ID. The profile records accepted Run ID
1401, which already exists and cannot be reused for a new launch.

The configured Stage-A dependency is
`Trained_Results/ThermalChannel/Local_Module_Runs/thermal_disk/Run_0000_base/best_model.pt`.
It is loaded strictly, including its normalization state, and frozen. Use
`--local-checkpoint` only when intentionally overriding that dependency for a
new run.

A bounded lifecycle smoke test can use one train and validation batch:

```bash
python train.py \
  --config src/config_core/forward/stage7_structured_context.json \
  --run-id 1500 \
  --epochs 1 \
  --max-train-batches 1 \
  --max-val-batches 1 \
  --device cuda:0 \
  --yes
```

This creates a real managed run and consumes the selected Run ID; it validates
the lifecycle but is not meaningful scientific training. The unbounded
Stage-7 profile requests 5000 epochs, so always review `--dry-run` before
launching with `--yes`.

## 2. Current model in one view

```text
physical modules + operating conditions + arbitrary field queries
                              │
                              ├─ ThermalChannel input/global adapter
                              ├─ 24 x 8 physical environment tokens
                              ▼
                    reusable HONF encoders
                              ▼
                  fixed K=6 softmax organizer
                              ▼
                     predicted angular ports
                              ▼
                frozen Stage-A disk surrogate
                              ▼
           local-response fusion + one refinement
                              ▼
                    final fixed organizer
                              ▼
    fused dense pairwise + hyper + global + near context
                              ▼
 [u, v, p, omega, T] + internal temperature + interface [T, qn]
```

The reusable core never imports ThermalChannel. The case package owns physical
feature definitions, environment/query geometry, datasets, Stage-A coupling,
Robin flux correction, field names, physical losses, plots, and inverse-facing
functionals. The top-level launchers discover it through
`channelthermal.plugin:create_plugin`.

The current core settings are:

| Setting | Stage-7 value |
|---|---|
| Organizer | `fixed_projection` |
| Hyperedges | 6, all active |
| Module/environment/query normalizer | softmax / softmax / softmax |
| Environment/query locality | none / none |
| Hyperedge state | organizer state used directly |
| Decoder | `enhanced_honf_pairwise` |
| Field assembly | `context_fusion` |
| Pairwise aggregation | historical reference `edge_explicit`; promoted overlay `fused_query_module` |
| Routing execution | dense full-beta training; gathered beta-0.98 evaluation override |
| Query edge/module limits | 0 / 0 (unlimited) |
| Hidden width / dropout | 256 / 0.0 |
| Environment grid | $24\times8=192$ tokens |
| Fourier frequencies | 4 for position, query, and pairwise geometry |
| Geometry | nonperiodic |
| Stage A | frozen, predicted ports, one refinement |

The decoder combines query-to-hyperedge value context, hypergraph-gated
query/module pair context, the global token, and Gaussian near-module context:

$$
c_q=c_q^H+c_q^{pair}+c_q^{global}+c_q^{near},
$$

$$
\widehat U(q)=H_{field}(\operatorname{LayerNorm}(c_q)).
$$

This is context fusion, not an exact additive decomposition into per-edge
physical fields. See [Model_Explain.md](Model_Explain.md) for the tensor
contracts, equations, Stage-A coupling, training objective, and compatibility
details.

## 3. Configuration model

A launch composes:

1. one strict core profile under `src/config_core/`;
2. the referenced case profile;
3. an optional experiment overlay;
4. allow-listed CLI overrides.

The current files are:

| Purpose | Configuration |
|---|---|
| Recommended forward profile | `src/config_core/forward/stage7_structured_context.json` |
| ThermalChannel data/model/loss policy | `Case_ThermalChannel/configs/case_default.json` |
| Profile status and ownership | `src/config_core/forward/profile_registry.json` |
| Historical Run-1000 profile | `src/config_core/forward/enhanced_honf_pairwise.json` |
| Stage-1–6 research base | `src/config_core/forward/adaptive_sparse_additive.json` |
| Current inverse topology-set template | `src/config_core/inverse/train_inverse_topology_set_template.json` |

The registry recommendation and CLI fallback are currently distinct:
`train.py` and `evaluate.py` still use `enhanced_honf_pairwise.json` when
`--config` is omitted. Pass the Stage-7 path explicitly for current scientific
work.

Core profiles own generic architecture, optimization, checkpoint policy, and
run identity. The case profile owns dataset selection, physical features,
Stage-A dependency, local coupling, corrections, losses, and evaluation
defaults. Unknown fields and ownership violations fail before training.

`project://...` resolves from `HONF_Proj`; `config://...` resolves from the
containing configuration file. Managed runs save source configs, CLI
overrides, resolved config, hashes, software state, and Git provenance.

## 4. Installation and external data

Python 3.10 or newer is required. Install PyTorch for the local compute
platform, then install the project and optional development dependencies:

```bash
conda activate ModularDT
python -m pip install -e . -e ./Case_ThermalChannel
python -m pip install -e '.[dev]'
```

Datasets stay outside Git. Copy and edit the local path map:

```bash
cp Case_ThermalChannel/Dataset/dataset_locations.example.json \
   Case_ThermalChannel/Dataset/dataset_locations.local.json
```

| Dataset ID | Purpose | Manifest split |
|---|---|---|
| `thermal_disk_local_v1` | Local Stage-A disk responses | 919 train, 115 test |
| `thermal_channel_global_v1` | Coupled global/local fields | 600 train, 90 test |

The path map is ignored by Git. `HONF_DATA_ROOT` may instead point to a parent
containing `Processed_LocalModule_Dataset/` and
`Processed_ChannelThermal_Dataset/`.

Validate files and manifest hashes with:

```bash
python tools/inspect_dataset.py --dataset-id thermal_disk_local_v1 --sha256
python tools/inspect_dataset.py --dataset-id thermal_channel_global_v1 --sha256
```

Physical definitions and the packed schema are documented in
[PHYSICS_AND_DATA.md](Case_ThermalChannel/Dataset/PHYSICS_AND_DATA.md).
PyTorch checkpoints are trusted pickle-based artifacts; never load an
untrusted `.pt` file.

## 6. Training and resume

The Stage-7 profile specifies AdamW with one parameter group, learning rate
$3\times10^{-4}$, weight decay $10^{-5}$, gradient clipping at 1.0, AMP off,
seed 0, predicted ports, and a 5000-epoch budget. The case profile uses 1024
sampled points per case, batch size 48, normalization, dynamic module padding,
and module-count bucketing.

Start a full run only after reviewing the dry-run:

```bash
python train.py \
  --config src/config_core/forward/stage7_structured_context.json \
  --experiment-overlay src/config_core/forward/experiments/stage7_fused_query_module.json \
  --run-id 1500 \
  --device cuda:0 \
  --yes
```

Resume a managed run in place from its retained compatibility checkpoint:

```bash
python train.py \
  --config /path/to/the/original/core/profile.json \
  --resume-checkpoint Trained_Results/ThermalChannel/HONF_Forward_Runs/Run_####_<timestamp>_<name>/latest_model.pt \
  --device cuda:0 \
  --yes
```

Resume validates immutable case/model/data/loss identity, strict model state,
optimizer groups and parameter order, AMP scaler, epoch, best metrics,
selection progress where applicable, and Python/NumPy/Torch/CUDA RNG state.
Run IDs are unique within each managed family and are never overwritten.

## 7. Evaluate the accepted model

Evaluate Run 1401 best-by-field directly:

```bash
python evaluate.py \
  --config src/config_core/forward/stage7_structured_context.json \
  --workflow forward \
  --checkpoint Trained_Results/ThermalChannel/HONF_Forward_Runs/Run_1401_20260823_151126_stage7_modern_structured_context/checkpoints/best_field.pt \
  --case-id 0653 \
  --device cuda:0 \
  --organization-view all \
  --routing-view summary
```

Evaluation reconstructs the checkpoint-owned model/configuration and loads the
state strictly. A timestamped job uses the canonical layout:

```text
evaluations/single_case/<case>_<timestamp>/
├── fields/
├── metrics/metrics_predicted.csv
├── arrays/evaluation_outputs_predicted.npz
├── organization/
├── routing/                              when requested
├── diagnostics/
├── plans/
├── summary.json
└── evaluation_manifest.json
```

Managed training runs retain legacy workflow filenames while also materializing
canonical checkpoints under `checkpoints/`:

| Canonical file | Selection criterion |
|---|---|
| `best_total.pt` | total validation objective |
| `best_field.pt` | global field MSE |
| `best_temperature.pt` | temperature MSE |
| `best_autonomous.pt` | predicted-port validation |
| `latest.pt` | latest resumable state |

For a new deployment or inverse-data build, choose the checkpoint by the
scientific acceptance criterion and record its SHA-256. Run 1401's accepted
baseline is `best_field.pt` at epoch 4585.

## 8. Compatibility and research modes

Saved configs missing newer mode fields resolve to fixed projection,
`residual_concat`, context fusion, softmax assignments, and dense execution.
Only mode-specific modules are instantiated, so historical checkpoints do not
gain unexpected parameters.

The profile registry records current, compatibility, and frozen-experiment
status without rewriting historical JSON. Supported research mechanisms
include:

- fixed or exchangeable organization;
- all-edge or quality/coverage selection;
- softmax, entmax15, or scheduled assignments;
- raw/residual or descriptor-first mechanism state;
- context-fusion or exact background-plus-edge assembly;
- dense or gathered execution;
- schema-v3 unordered topology export.

Use `adaptive_sparse_additive.json` and its registered experiment overlays only
when intentionally reproducing Stage-1–6 work. The next forward phase is sparse
execution for the accepted context-fusion model, with numerical parity as a
hard gate.

## 9. Inverse design

The maintained inverse core supports both historical indexed compact plans and
schema-v3 exchangeable topology sets. The current topology-set template uses
shared token projections, permutation-equivariant set attention, Sinkhorn
matching, and set cross-attention from physical module slots to active plan
tokens. It requires the exact SHA-256 of the forward checkpoint that generated
its targets.

Inverse candidates must be ranked by a frozen autonomous forward checkpoint
and then verified by the appropriate high-fidelity physical workflow. Neither
forward nor inverse neural predictions replace engineering validation.
