# General observation and response training

This path trains one joint predictor of the configured physical-field components. It keeps the ordinary native field objective and can add errors at existing observations, differences between two observed scenes, and differences between those scene changes at neighboring observation positions. Both scenes are actual saved cases; their difference includes every changed prescribed input and is not a new solved edit or a physical derivative. The configured output width is fixed for a trained model, but the shared path does not require a particular number or name of fields.

Each observation block describes field names and units, output-column maps, positive TRAIN-only scales, original case and receiver identities, partition, coordinate frame and time meaning, coordinates, component-validity masks, physical measures, and views of existing reference values. A sparse linear extraction map states every required joint-field query and its output column and coefficient. It can describe a direct field, interpolation, or a saved differential observation. Source references retain their source precision. Scene observations, pair correspondence, and meaningful spatial edges have separate masks; a missing reference is never a zero label.

The shared runtime draws a positive-weight block and a uniformly sampled seed with replacement, then one of at most four nearest compatible distinct observations. Receiver identities break distance ties; declared groups prevent edges between disconnected supports or unrelated members. Fixed precomputed component-specific eligible masses and proposal probabilities correct the estimator. Repeated draws contribute repeatedly even when their required field queries are deduplicated. A seed without a neighbor retains its absolute and eligible point-response terms. The runtime groups exact query dependencies by scene, coordinate frame and time, prepares each group once for the auxiliary presentation, decodes full and restricted joint fields, applies the adapter's existing physical output scale and offset, and gathers every requested observation. This does not merge the separate native training visits or establish an end-to-end speedup.

Thermal uses the saved physical cell centres for the fixed-frame `u`, `v`, `p`, `omega`, and fluid-temperature measurements. Vorticity is the existing linear finite-difference extraction from joint velocity outputs. The common pair support is one sampling block with weight 1; each scene's fluid support without a corresponding observation is a separate block of weight 0.5. Material temperature, surface temperature and normal-flux proxy, and outside temperature each have two separate scene blocks with weight 0.5 per scene; their native component weights and TRAIN scales are retained. Material observations use the stored local points inside each circular member. Surface observations use its 64 saved angles; outside observations use points displaced a fixed distance outward from those same angles. These local module slots are not persistent identities between independently generated scenes, so these blocks provide absolute observations only. The normal-flux proxy is the surface-minus-outside temperature divided by that saved distance and multiplied by the existing effective conductivity; it is not an added physical-law loss or an independently verified conservative flux. Source values and coordinates in the current packed Thermal data are FP32 and the native extraction uses FP32 geometry; no edited labels are loaded.

The Wind binding uses existing saved three-component velocities, compatible steady frames and explicit linear native-centre interpolation. Its declared finite input-only population of common positions and quadrature masses is a sampled observation measure, not a whole-volume evaluation. The current Wind `coupled_native_capability()` reports that coupled-native mode is unavailable until the binding exposes its native sampling law, row budget and complete per-row execution and extraction dependencies. Ordinary native training and the independent-observation interface remain available. The small analytic fixture uses seven coupled outputs, variable original-member counts, three-dimensional ragged observations, unequal measures, missing component values and a block without pair correspondence. It provides general software portability evidence, not Wind physical-learning validation.

## Reuse ordinary native predictions for observed changes

The optional `observation_response.mode: coupled_native` path coordinates the ordinary native observation samples of two saved scenes. For example, if both scenes contain a valid velocity observation at the same physical position and time, the runtime can subtract their existing predicted velocities and reference velocities before the native backward calculation. Each scene still receives its ordinary number of distinct native row IDs. A row without a corresponding physical meaning keeps its ordinary absolute supervision. No additional scene prediction, edited label or physical solve supplies this response term.

The three named variants are `native_control`, `observed_response` and `sampled_reader_response`. They share the native membership, pair-aware case order, query budgets and query streams. The control uses the native objective and records response coverage without constructing a response gradient graph. The second variant adds the supported observed-change error to the same two-reader predictions. The third executes one sampled reader for a complete effective batch, with the same reader for both endpoints of every pair. A trained model still supports ordinary standalone full or restricted inference; it is one joint predictor of all configured fields.

For native uniform sampling without replacement, shared code first draws IID anchor rows by maximal coupling: common physical keys have their minimum probability mass, and the residual branch supplies the remaining mass of each scene. Coordinate multiplicities remain part of those probabilities. After deduplicating anchor row IDs, it uniformly completes each scene to its original row budget and independently shuffles the panel. This preserves the entire native uniform-subset and ordered-panel law, including a native loss that divides by its realized valid mass. Repeated coordinates remain distinct native rows, and repeated anchor draws retain repeated response contributions. It preserves the sampling distribution rather than historical query draws or optimization trajectories.

The implemented coupled-native row law is `uniform_without_replacement`, which the binding explicitly declares for each scene through `coupled_native_sampling_law(case_id)`. A pair with unsupported or mismatched laws remains on its ordinary native sampling path and is reported unavailable for coupling. If no training pair has a supported response component, the coupled attachment cannot proceed. Other native samplers, such as weighted or with-replacement draws, require their own correctly matched coupling implementation; they must not be declared as uniform merely to enable this path.

The response reducer compares prediction-minus-reference residuals at genuinely corresponding observations, divided by their existing positive TRAIN scales. It uses fixed common component physical masses, the original number of anchor draws and the inverse probability of each common row-pair draw. It never divides by the realized number of matches. A zero-match draw contributes zero to an available estimator; a component without eligible population mass is unavailable. Proposal probability and physical measure have different roles. The implementation is in `src/honf_runtime/coupled_observations.py`; it does not call the model or materialize all possible row pairs.

Reader sampling targets the existing weighted two-reader objective. If reader `v` has objective weight `w_v` and sampling probability `p_v`, its executed view-dependent native and response terms receive `w_v / p_v`. With both weights and probabilities equal to one half, the factor is one. View-independent terms execute once at their original weight. The unused reader is absent rather than recorded as a zero loss. The unclipped gradient has the correct conditional expectation; clipping and AdamW can produce different learning trajectories. Scheduled validation executes both readers. Complete process timing and executed member/head work establish any acceleration claim.

The optional `anchored_checkpoint_integer_plans(True)` context retains integer membership and union indices only for the lifetime of a checkpointed prediction graph. Floating priors, anchor weights, scores and values remain differentiable. Index reuse is disabled by default: the R17-11 complete-epoch probes preserved losses, gradients and optimizer values, but showed inconsistent timing and substantially higher allocated memory. Ordinary training uses index rebuilding; single-reader execution remains a separate operation.

An adapter exposes its actual native row population and native budget through `coupled_native_population(case_id)` and `coupled_native_budget(case_id)`, explicitly declares `coupled_native_sampling_law(case_id)`, identifies view-dependent native terms with `coupled_view_loss_names()`, and exposes already-extracted native values plus actual executed dependency IDs through `coupled_native_extraction(predictions, batch_index, batch)`. It constructs the same native carrier for a declared validation pair through `coupled_validation_batch(pair, sample)`. A `NativeObservationPopulation` supplies exact frame/time/coordinate/correspondence keys, component identities and units, references, physical measures, validity, extraction identity and guaranteed native dependencies. Shared code owns row coupling, completion, response reduction, reader selection, calibration and recovery. Independent local member slots are not persistent member identities, and nearby coordinates are not rounded into correspondence.

Only observations whose complete extraction dependencies are guaranteed by ordinary native execution may contribute. Reusing an interpolation or differential observation requires its existing complete stencil, not just its central position. Unsupported sampling laws or extraction components retain ordinary native supervision and report their reuse capability as unavailable. The coupling metadata cache retains immutable observation/index information only, within a declared per-process byte limit; it never retains a learned context across parameter updates.

Fresh coupled comparisons start from one actual saved epoch-zero state per membership cohort. Their model tensors, normalization, fresh optimizer, RNG and provider state are shared before fitting, with organization and schedule clocks at zero. Calibrate the response coefficient on the declared approximately ten-percent TRAIN panel using both readers, restore the unchanged state, and use the same coefficient across response variants. The response ramp is positive from epoch 1 through epoch 50. The saved run definitions own recording and loss accumulation order on resume; JSON object-key order does not redefine either. Historical native-prefix recipes remain readable with their original semantics.

An optional finite positive `observation_response.response_weight` multiplies the calibrated coupled response contribution in TRAIN and dual-reader validation; its default is `1.0`. It leaves the shared epoch-zero calibration, native losses, observations and reader probabilities unchanged. A nondefault value is saved in the run's scientific identity and loss definition, so it cannot be changed during ordinary resume. The independent observation evaluation remains a separate unweighted measurement.

## Extending a saved observation-response lineage

An authorized continuation beyond a saved execution horizon uses the same run and its saved recipe, for example:

```bash
python tools/relation_anchored_train.py fit --recipe <run>/configs/resolved_config.json --output <run> --device <runtime-device> --resume latest --extend-horizon --stop-after 1000
```

The option extends only the execution horizon and adds future 100-epoch checkpoint milestones. It retains existing milestones, the original recipe's `local_horizon`, saved optimizer schedule, model and optimizer state, provider and sampling state, objective, recording definitions, and histories. The native provider's execution-only sampling bound is extended where required. Later ordinary resumes within the saved execution horizon do not need `--extend-horizon`; a further increase does. Scientific identity changes, including a different response weight, are rejected. GPU selection remains a runtime choice. This mechanism does not authorize a continuation by itself.

## Evaluate saved native fields

`tools/thermal_native_checkpoint_evaluate.py` restores the native joint-field predictor, saved normalization and original data binding without opening training-only response corpora. It supports preserved Thermal state-response, native-pair, field-response, local-response and observation-response checkpoints, plus the historical R16-10R predictor. Use a literal checkpoint path to distinguish the final epoch from an independently selected best-field alias. This inference path does not resume training or change either checkpoint.

For a declared small panel, run `python tools/thermal_native_checkpoint_evaluate.py --checkpoint <checkpoint.pt> --cases <comma-separated-original-case-ids> --read-mode both --near-object-errors --query-tile-size 1024 --device <runtime-device> --output <new-DATA2-file.json>`. `--export-cases` saves at most four selected physical-field arrays with their references, masks and coordinates. The result retains separate reader reductions, physical field means and tails, per-case member maxima, complete panel times and runtime precision/device metadata. CUDA runs also record allocated and reserved peaks. These are complete evaluation passes rather than repeated isolated inference benchmarks.

Use `--all-original-held-out` instead of `--cases` only when full-population evaluation is explicitly authorized. It selects the existing canonical 89 original held-out cases in source order, excluding case 0273 because it overlaps training membership. These records have historically been used for development; expanding coverage does not make them a blind test. “Full reader” means access to all permitted prepared members and does not describe population coverage. The inference tile controls execution only and leaves the saved training tile, native observations and physical extraction unchanged.

## Maintained CPU example

For the coupled native path, run `CUDA_VISIBLE_DEVICES='' python tools/example_coupled_native_recovery.py --output-root /data2/YOUR_USER/ModularDT/coupled_native_example` from the repository root. This seven-field software fixture prepares a common actual epoch-zero state, fits one uninterrupted two-epoch lineage and one resumed lineage, reloads a saved configuration with reordered JSON keys in a fresh process, and compares model/optimizer/RNG/sampler/provider/selector state, ordered losses and columns, and dual-reader validation. It charges four tiny fixture epochs. It tests software recovery rather than physical learning quality.

For a sampled-reader native or finite-observation recipe, `python tools/verify_coupled_native_recovery.py --recipe <recipe.json> --output-root <new-DATA2-directory> --device <runtime-device>` exercises two uninterrupted epochs against one committed epoch followed by a fresh-process continuation. It keeps the recipe's full scientific horizon and learning-rate schedule. The check compares saved training state, ordered recording definitions and values, validation, and the next native and four reader draws. Finite-observation runs additionally compare saved coefficients, selected probe rows, physical measures and extraction definitions with the rebuilt provider. A provider without the coupled sampler uses its own `make_batch` receiver rows for this check. This is four qualification epochs, with GPU visibility selected separately at runtime.

The [finite-observation guide](Finite_Observation_State_Response.md) describes point anchors and scene-summary contrasts on independently selected source supports, including a native path without any coupled-row capability. Actual round recipes, shared initial states, budgets and declared panels belong in the local experiment plan and report.

From the repository root, run the following with a new empty output directory on the mounted DATA2 filesystem:

```bash
CUDA_VISIBLE_DEVICES='' python tools/example_observation_response_fixture.py --output-root /data2/YOUR_USER/ModularDT/observation_example
```

The example runs the public `tools/relation_anchored_train.py` entry point for one uninterrupted two-epoch fixture and one one-epoch fixture followed by a fresh-process resume using its saved `configs/resolved_config.json`. It compares model, optimizer, random-generator, sampler, provider, selector and ordered recording state, together with recorded loss values and validation history. It then runs `tools/observation_response_evaluate.py` on the explicitly declared two-scene fixture panel and writes separate full/restricted physical observation metrics. The example coefficients are fixed fixture values, not a calibration or a scientific recommendation. Its run folders contain `metrics/history.csv`, `metrics/validation.csv`, configuration and recording definitions, loss-curve PDF/PNG files, model checkpoints, process logs and a compact recovery receipt.

## Adding an adapter

A collaborator can point `observation_response.adapter_factory` in the run recipe to an importable `package.module:factory` callable. The factory receives the recipe, runtime device and optional resume payload, and returns the ordinary native `(model, provider, binding)`. Existing built-in capabilities are `thermal`, `wind`, and `analytic_fixture`; registration through `register_observation_capability` also supports a Python application that installs its own binding before calling the public builder.

Set `observation_response.enabled` to `false` to build and train the ordinary native model/provider without observation blocks, pair selection, auxiliary state, or auxiliary columns. Legacy native-only profiles also continue to work.

The binding supplies `identity_payload()`, a stable `block_names()` inventory for realized draw and edge recording, reproducible input-only `training_pairs()` and fixed `validation_pairs()`, `calibration_case_ids()`, `native_case_key(case_id)`, `validate_pair(pair)`, `observation_blocks(pair)`, and `field_request(model, case_id, dependencies)`. The last method returns the target-free native scene and query carriers plus per-output physical scale and offset; it does not evaluate a loss or choose a model-error-dependent pair. For a separately declared exposed evaluation panel, an optional `for_evaluation(pairs)` returns a read-only binding without altering the training membership or its saved identity.

For each block, state whether correspondence is `fixed_frame`, genuinely `member_attached` with persistent original member IDs and a coordinate transport, or `none`. Supply component validity and physical measures for individual observations, pairs and edges separately. Provide a distinct proposal block when pair and individual support differ, and use stable receiver identities and groups that reflect actual physical connectivity. Do not infer identity from nearest geometry, change reference precision, create edited observations, add case-specific objective logic, or assume that a channel index implies physical equivalence.

The R17-10 children share their pair schedule, seed draws, extraction maps and epoch-10 TRAIN-only gradient calibration. Their extra absolute, point-response and spatial-response coefficients target native-gradient ratios 0.25, 0.10 and 0.05 and use the same epochs 11–50 ramp. A zero coefficient still executes the same observation draws and joint predictions, preserving matched exposure. The common prefix and its saved calibration are initialized explicitly using `tools/observation_response_prepare.py` and the native-prefix branch; ordinary resume does not change an existing objective or its recording definitions. Full scientific training and the fixture have different purposes and budgets.

For GPU recovery that requires identical numerical results, save `execution_config.deterministic_algorithms: true` in a new observation recipe. The public launcher sets the deterministic PyTorch algorithms and cuBLAS workspace policy before CUDA initialization. R17-10 qualified this setting with two repeated uninterrupted Thermal fits and an actual committed-checkpoint interruption followed by a fresh-process saved-configuration resume; model and optimizer tensors, RNG, sampler, provider state, ordered loss records and validation values matched exactly. Timing values are measured independently. This opt-in setting leaves historical profiles and recipes unchanged and does not select a physical GPU.
