# Case response evaluation

A finite response compares complete baseline and edited executions. Rebuild each scene and query after changing geometry or controls. `honf_runtime.response_evaluation` exposes in-memory preparation, native extraction, actual traces and executed-work counts. Its outputs are model evidence; callers supply matching physical references and must separately assess response accuracy. Instrumented timings include tracing.

For Thermal, `channelthermal.physical_response.compare_native_response` accepts named native observations at both endpoints, each with prediction, physical reference and validity mask arrays. Align original member IDs, coordinates, receiver roles, field units and input controls before calling it. Endpoint metrics use each endpoint's own valid support; finite-change metrics use their intersection. Fixed fluid receivers and moving material or interface receivers require their respective matching conventions. Optional frozen-local observations can be supplied as additional explicitly aligned named fields; they are not required for direct native comparisons.

`summarize_actions` reports equal-family error, reference effect, resolved sign and ordering with caller-supplied positive resolution floors and explicit coverage. `channelthermal.native_functionals` provides masked material-temperature and pressure functionals; its smoothing scale and pressure bands must match the reference calculation. Physical accuracy and design ranking require matched physical references; a model derivative or learned relationship alone does not establish either.

`honf_runtime.state_response.compare_aligned_response` validates ordered original receiver IDs before comparing field endpoints and common-support changes. For a requested finite decision pool, `evaluate_candidate_pool` accepts predicted and optional matching physical deltas indexed by action and named observable. The caller specifies the objective to minimize, upper constraint caps, objective scale, sensitivities and a baseline whose deltas are zero. With physical observations it reports selected-action constraint violations, false feasible/rejected actions, physically resolved improvement and regret within the supplied pool. `raw_improvement` is the negative physical objective delta of the model-selected action; `accepted_improvement` uses the action retained after physical feasibility checking. Positive values indicate improvement for the minimized objective. An infeasible selected action falls back only to a physically feasible baseline. Without physical observations it reports the model choice and leaves both improvement fields, physical verification and acceptance unavailable.

`channelthermal.physical_response.evaluate_thermal_candidate_pool` supplies the Thermal J/P convenience interface. Each action must include both native-unit J and P deltas; objective, caps, scales and sensitivities remain explicit caller inputs. These comparisons establish evidence for the measured finite pool only, not general inverse-design validity.

The legacy Thermal response CLI requires an explicit `--labels` file for the requested role, or `thermal_state_response.functional_label_paths` entries in the recipe. Use `--labels` when a saved recipe lacks this mapping so the recipe identity remains unchanged. Without a selected panel, it uses the first approximately 10% of role families; `--all-families` explicitly selects the complete role. The native evaluation CLI similarly selects the first approximately 10% of available cases unless `--cases` or `--all-cases` is supplied. For the new profile, its already sampled validation panel is used as saved, without resampling. Match the selected IDs across models.
