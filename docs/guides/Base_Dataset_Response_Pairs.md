# Response supervision from existing physical-field samples

A case with saved physical fields can supervise changes without running another simulator. Load two existing TRAIN scenes, predict each scene, and compare the predicted change with the change between their saved references. Store their case IDs and the comparison definition; do not copy their fields into a second dataset. Native field training remains available without any response provider.

For example, two saved scenes have pressure drops 1.0 and 1.4 in the case's pressure units. Predictions of 1.1 and 1.3 give a predicted change of 0.2 rather than the saved change of 0.4. The additional error is -0.2. The case must also say which inputs changed: this comparison could involve different layouts, heating or inlet conditions. It does not automatically measure the effect of moving one object while holding everything else fixed.

## Implementation status and default path

The shared `honf_runtime.state_response` module provides native-pair selection, scheduling, alignment checks and difference reductions. The Thermal `native_pair` profile retains the historical four-observation recipe. The `field_response` profile adds common-position physical-field comparisons through `tools/relation_anchored_train.py`; both use the shared CSV recorder. The optional [local multisecant profile](Local_Multisecant_Response_Training.md) extends common-position comparisons to input-selected neighborhoods with a bounded conditioned contrast. Interface correctness and a working training path do not establish learned prediction or response gains. Existing Thermal `state_response` recipes use the separate edited-scene provider documented in [state-response training](State_Response_Training.md); retain that provider and its checkpoints for historical reproduction.

The supported development order is native field loading and prediction, optional comparisons drawn from that same dataset, then any explicitly requested specialized intervention study. No extra edited-scene H5, physical solve, synthetic field label or Thermal-specific manifest may become a requirement of the shared native-pair interface. Existing extra-response data must not silently enter fitting, normalization, response scales or calibration in a base-only experiment.

## Share one TRAIN calibration

For matched Thermal anchor and contrast runs, use one calibration measured from the anchor's epoch-10 TRAIN state. Pass `--native-pair-calibration-output PATH` to the anchor's `tools/relation_anchored_train.py fit` command. Under the run's existing writer lock, the anchor atomically publishes the record before its first auxiliary update, or at the first resumed epoch if its calibration is already saved. Start the contrast only after that record exists, and pass `--native-pair-calibration-input PATH` to its fit command. The contrast uses the exact published absolute and contrast coefficients; it does not independently recalibrate. The record checks native TRAIN membership, dataset binding, matching, scales, sampling and objective definition. Both flags are runtime paths and do not alter the resolved recipe.

A separately named anchor run may also consume that same record with `--native-pair-calibration-input PATH`. Use this for a matched execution comparison so changing batching does not independently recalibrate its loss weight. The same membership, normalization, pair, scale and objective checks apply. Choose exactly one input/output flag; an existing run keeps its recorded calibration and adoption history.

An existing contrast lineage may explicitly adopt the shared record on a same-run resume by passing the input flag once. Its model, optimizer, RNG and sampler continue from the saved checkpoint. The run retains `configs/native_pair_calibration_reference.json`, an atomic before/after adoption receipt in `logs/`, and the adopted calibration in provider checkpoint state. Later resumes need no calibration flag. The source run and completed epoch in the shared record identify when it was published; a latest-checkpoint alias can subsequently advance. Report any earlier independently calibrated epochs and their actual coefficients in the local experiment report rather than rewriting those checkpoints or histories.

## What the comparison learns

For an observable extracted by the case, write its prediction error in scene i as e_i = predicted value minus saved reference value. A normalized pair penalty is `(e_B - e_A)^2 / s^2`, where s is a positive scale obtained from TRAIN. Absolute supervision of the two scenes is still necessary: the same wrong offset in both predictions disappears from their difference.

This penalty uses existing information. Algebraically, `(e_B - e_A)^2 = e_A^2 + e_B^2 - 2 e_A e_B`; it changes which relative errors and correlations training penalizes, rather than supplying a new physical observation. For uniformly weighted comparisons of every pair, it reduces to a scaled variance of the existing residuals. A sparse, input-selected set is useful for controlling work and emphasizing available input changes, but cannot create a physical intervention absent from the base samples.

The adoption question has two parts: whether a base-only recipe provides useful field accuracy at acceptable cost, and whether adding its difference penalty improves change prediction over a matched absolute-field control. Compare separate fresh models with identical initialization, native case visits, auxiliary absolute labels, physical query positions, sampling and schedules. Only the difference contribution changes. A historical response-trained checkpoint is a practical reference, not that causal control; initializing from it would inherit the extra corpus's influence.

## Common-position field training and a shared native prefix

The Thermal `field_response` profile has three descriptive variants: native fields alone, the same native fields plus sampled paired absolute fields, and those same labels plus pointwise field differences. A case supplies a joint predictor, not a separate response head. Thermal compares u, v, pressure, vorticity and fluid temperature at positions valid in both scenes; J/P and regional summaries are optional evaluation measurements. Native surface, material, outside-temperature and proxy objectives remain part of ordinary training. The auxiliary call requests only the fluid fields and their required interpolation/curl support.

For each eligible source list, sample up to 128 saved observation rows uniformly without replacement. Each row retains its original weight and a factor equal to the eligible population count divided by the draw count and full eligible channel weight; each scene contributes half the comparison measure. Keep duplicate row mass. This estimates the symmetric saved-observation measure with a fixed denominator, not uniform physical area and not a ratio normalized by random sampled mass. Unavailable channels contribute no target or channel weight, and pair averaging retains the scheduled pair count. Arithmetic unbiasedness assumes fixed per-position predictions; companion-query and role-union numerical differences must be measured and disclosed separately.

Use one native-only state through epoch 10 with full optimizer, RNG, native sampling and normalization state. Retain the literal `checkpoints/epoch_0010_model.pt`, finish its writer, and calibrate both auxiliary coefficients once with `provider.calibrate_common_prefix(model, epoch=10)` on its declared TRAIN pairs without an optimizer update. Save that compact record once. `tools/field_response_branch.py --recipe CHILD_RECIPE --source PREFIX_CHECKPOINT --calibration CALIBRATION_JSON --output CHILD_RUN` initializes a new paired child using the existing CSV/checkpoint formats. The child inherits all ten native scalar rows with future auxiliary columns blank and starts selectors from the literal inherited snapshot. It then uses ordinary `tools/relation_anchored_train.py fit --resume latest`; an ordinary resume never changes objectives or rewrites schemas.

The branch operation verifies unchanged native data, architecture, observations, objective, sampling, schedule, and ordered native scalar meanings. Each paired child uses its own output identity and the same saved calibration, absolute labels, selected pairs, common positions and full/restricted reductions. Coefficients remain fixed while their multiplier is zero through epoch 10 and ramps through epoch 50. Absolute schedules retain their original age and horizon across review stops. A fresh-process regression must test both native and active auxiliary recovery, saved-configuration reload, exact state and loss values, and scalar append order.

`tools/thermal_field_response_evaluate.py` evaluates declared matched panels with restricted access as primary and full access as a separate diagnostic. Its primary `D_delta` averages each pair's physical common-cell RMSE within each channel before combining TRAIN-scaled channels with native weights. The exact saved-observation measure is a separate diagnostic. Pass `--thermal-functionals` to include case-owned J/P and regional-temperature changes; those summaries do not enter the shared field loss. Keep original dataset split labels and report historically exposed development panels honestly rather than presenting them as independent TEST.

## Small case interface

Extend the existing native case adapter rather than introducing another dataset framework. The following are the required responsibilities; concrete class names should follow the maintained provider interfaces when implemented.

| Operation | Case supplies | Shared code supplies |
| --- | --- | --- |
| Describe an existing sample | Original case ID/split, input-only compatibility keys, physical coordinate frame, prescribed-input descriptor and original member IDs if present | Split-safe selection, deterministic pair scheduling and compact case-ID references |
| Prepare a comparison | Two existing native sample references; query positions and transformations; valid masks and physical measures; named observables and their units; any verified member correspondence | Loading through existing readers, bounded batching, prediction reuse and accounting for extra queries |
| Extract observations | Differentiable predicted observations and matching saved observations, using the same extraction, support and units | Normalized absolute/difference reductions, declared weights, TRAIN-only scale/calibration plumbing and ordinary metric records |

The adapter does not serialize the whole source dataset, own another optimizer, or implement its own logging tree. Shared code must not import Thermal, Wind or geothermal modules to calculate a loss. A minimal pair record contains the two original IDs, split, input-change description and reference to its observation recipe. Large masks, coordinates and fields stay in their original shared source, or in one explicitly budgeted reusable input artifact if computation genuinely requires it.

For a new dataset, reuse its native loader and add the input description and observation extraction. If it has no valid way to compare two fields at common positions, it can still compare compatible scalar observables. If it supplies neither, native training remains supported and response supervision is unavailable; do not invent correspondence or replace missing targets with zero.

The shared `FieldResponsePair` accepts a separate, potentially different-length observation list per pair. Its predictions have axes view, scene, receiver and channel; references have scene, receiver and channel axes. The case supplies a common-support mask and final per-receiver, per-channel integration masses, including any sampling-probability correction and fixed full-population denominator. The reducer does not divide by the observed sampled mass. It normalizes by the declared TRAIN channel scales, sums the declared channel weights without renormalizing absent channels, and averages views and pairs equally. It records eligible pair counts and effective channel weights. A case must determine eligibility from both scenes before supplying the observations.

`select_degree_two_native_pairs` retains the greedy disjoint matching and may add input-selected eligible edges only within the range of already matched distances in the same split and compatibility group, with no scene used by more than two edges. It does not replace the case's prescribed-input distance or physical-support checks.

## Positions, objects and physical measures

- A field difference requires predictions and references at the same physical positions in the same coordinate frame. Intersect the two physical validity masks and use the case's physical weights. Equal array shapes, sample indices or normalized coordinate values alone are insufficient.
- A temperature attached to a material point or a turbine-local measurement requires original identity and an explicit local-coordinate correspondence. An input-space assignment used to find similar layouts does not establish persistent object identity. Compare scene-level observables when such identity is absent.
- Scalar observables may use each scene's own support when that defines the same physical quantity, such as each scene's inlet-minus-outlet pressure drop. A regional temperature comparison uses one defined physical region and common valid positions in that region. Explain which operation applies.
- Keep interpolation, frame transformations and pressure reference conventions case-owned. Preserve source dtypes and coordinates; using FP64 for a reduction does not turn an FP32 saved field into a higher-precision observation.
- Fit normalizers, response scales and gradient balance from native TRAIN data only. State physical units, scale floors and zero-variation components separately. Validation and TEST pairs must contain only cases in their own declared panels; never pair across splits.

## Compatibility and provenance

The case adapter determines compatibility from the actual prescribed physics, physical coordinate and measurement definitions, and source-generation provenance. Exact equality of every JSON key is not itself a physical law: a record may contain derived controls, settings for a different simulator, or metadata irrelevant to the saved field. For example, a change in Reynolds number and its derived viscosity describes one operating-condition change, not two independent interventions. Record every actual prescribed change and verify any physical equivalence from the source recipe.

Missing historical settings are not established by inserting today's defaults. A verified historical default can support an explicitly documented comparison; otherwise retain the missing provenance and do not claim equivalence. Preserve the original JSON and numerical precision. Geometry assignment can identify similar sets of objects, but it does not establish persistent member identity; member-attached differences require independently verified correspondence. A case adapter supplies these meanings for its own dataset. Diagnostic metadata normalization does not alter existing pair graphs, identities or saved recipes.

## Pair selection and execution

Choose pairs using prescribed inputs, without model errors, target differences, response signs or design outcomes. Useful choices include existing repeated layouts with different operating conditions, or similar layouts within compatible domain/material/control groups. Record all inputs that actually differ. Exclude identical-input duplicates from informative response edges while retaining their ordinary native supervision.

Use a sparse pair list or reproducible sampler, not a materialized all-pairs field dataset. Keep every declared native case visit; an unpairable sample still contributes its native loss. A small rotating set of pairs can receive additional observation queries while the rest retain the ordinary native sampling. Both comparison arms execute the same scene-preparation and prediction operations at the same inputs/positions and receive the same absolute targets; only the added difference calculation changes. Their prediction values can differ as their weights learn. Co-locate paired samples when practical, reuse scene preparation and existing predictions, and charge any second decode explicitly. Do not retain an entire epoch's autograd graphs merely to pair distant batches.

Store the sampling method, seed, original membership reference and required sampler state. Per-epoch SHA summaries cannot restore sampling and are not a default substitute for that state. Record actual case/pair counts and useful executed-work totals. Use the [shared artifact contract](Run_Artifacts_and_Monitoring.md); no case-specific logging framework is needed.

New Thermal recipes explicitly set `thermal_native_pair.prediction_batching` to `paired`. The two scenes of each scheduled pair share one prediction call, then differentiable predictions are split before computing each scene's full/restricted losses and physical observations. This preserves individual masks, physical measures and equal-scene reductions; reducing both scenes as one design would change the objective. `serial` retains separate calls, and historical saved recipes without the setting retain serial execution on resume. Pair IDs, optimizer-update attachment, full labels, query tile size and activation checkpointing are unchanged. Fewer dispatches do not imply fewer physical predictions or a measured speedup: compare complete epochs, gradients and peak memory on the same runtime-selected GPU. Reusing sampled native predictions requires matching the actual physical positions and optimizer update; do not move pairs across updates or substitute sparse predictions for complete auxiliary labels.

## Thermal and other cases

Thermal's native dataset includes saved full physical fields, material temperatures and port observations. Existing helpers calculate the material-temperature smooth maximum J and inlet-minus-outlet pressure drop P in `channelthermal.native_functionals`. The regional helper in `thermal_native_port_task` is a historical example defined from its supplied baseline layout; a native-pair adapter must explicitly choose the region-defining geometry rather than assume symmetry or generic suitability. Each scene uses its own material and pressure-band validity for J/P; regional differences use one stated region and identical physical coordinates valid in both scenes. Arbitrary native layouts must not be forced into the historical baseline-plus-four-edits family class or subtracted by module slot.

The inspected Thermal base TRAIN data contains repeated-layout comparisons whose Reynolds number changes, and independently generated layouts whose heating also changes. These are different kinds of supervision. Neither provides a general fixed-heat, layout-only edit dataset. The analytic-wake benchmark's particular dependencies do not authorize a generic heat-independent flow model or a specialized prediction branch.

For optional input-only emphasis, `InputPairDescription` carries the case IDs, object count, structural and control distances, and case-owned frame, units and compatibility details. `fit_input_pair_weights` fits global TRAIN structural tertiles and average tied control ranks within count-band/tertile cells; it saves the descriptions, thresholds, rank maps and weights. `input_pair_weight` maps validation inputs using only those saved TRAIN ranks, clipping beyond their range and returning one for empty or constant cells. The Thermal adapter computes a geometry-only assignment in float64 and measures assigned heat differences using the prescribed heat range; the assignment is a comparison of sets and does not assert original module identity. `thermal_field_response.difference_weight_amplitude` enables the weighting on the difference loss only; absolute labels, physical masses and pair scheduling stay unchanged. The saved identity contains the fitted map, and the recorded unweighted difference and pair-weight sums make actual exposure inspectable. Smaller input control differences do not create fixed-control reference fields.

Another case supplies its own structural meaning, control scales, compatible inputs, frame and support. For example, a geothermal adapter could describe fracture geometry as structure and injection and boundary settings as controls, while specifying physical time and verified well identity for field or well comparisons. This describes an adapter contract, not an implemented geothermal training provider. Wind coordinates can rotate with wind direction, so transform to a common declared frame and verify layout identity before treating a coordinate difference as a structural change.

Wind has repeated layouts under different wind directions, but its saved coordinates and velocity components may be wind-aligned. A case must define whether observations refer to a wind-relative or Earth-fixed position and transform positions and vectors accordingly. Preserve source turbine slots; do not invent persistent identity metadata. Geothermal cases can use the same interface for pressure/temperature at declared physical positions or well observables; their meshes, well identities and integration weights belong in their adapter. Supporting this interface does not itself establish response accuracy in either application.

`windfarm.field_response.saved_velocity_pair` extracts three saved velocity components at common wind-relative positions from two rows of the same layout and distinct directions after checking the actual seed-42 grouped TRAIN membership. Its equal-position observation measure is a small reference-check example; Wind's native training uses five overlapping role measures, and a future fitting recipe must state its own measure and TRAIN scales. For geothermal, an adapter must also identify the physical time of each pressure or temperature reference, interpolate each native mesh in a declared frame, provide valid support and physical integration masses, and establish original well identity before comparing well-attached values. No geothermal training provider is implied by this interface.

R17-3 should demonstrate the interface with Thermal and a small Wind no-training example, plus a non-Thermal ragged/coordinate fixture. Additional case-specific training or new simulations require their own scoped task.

`Case_WindFarm/scripts/compare_native_pair.py` reads two supplied existing rows with a common layout and distinct directions. It interpolates each scene's pressure at the same two positions in the saved downstream/crosswind/vertical frame, then compares the within-scene pressure differences. The two positions are selected from the overlap of the saved coordinate ranges. This is a wind-relative scene observable, not an Earth-fixed comparison or a persistent turbine match; the user supplies a shared split label and is responsible for its membership. For a geothermal adapter, supply physical positions and integration measures for pressure or temperature, or identify corresponding wells explicitly before comparing well observables.

## Verification and decisions

Check direct native labels against adapter-extracted labels, source precision, masks/weights, role separation, deterministic pair schedules and predictions reused at aligned positions. A prediction equal to the saved reference must give zero absolute and difference loss; a common erroneous offset must remain visible to the absolute loss. Check differentiability and reject invalid alignment. Use a small interrupted/resumed example to verify actual model, optimizer, RNG and sampler state.

Report native accuracy, change errors in physical units, normalized aggregates, near-zero response handling and measured complete cost separately. Count contributing cases/layouts as well as correlated pairs. Apply approximately 10% matched model-evaluation coverage by default. If pair supervision ties or loses, retain the simpler base-only recipe; that does not make an extra physical-response corpus a mandatory fallback. A controlled-edit claim or verified inverse design requires the corresponding evidence and cannot be inferred from smaller field error.
