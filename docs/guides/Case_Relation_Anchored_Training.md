# Thermal and Wind relation-anchored training

The case providers use `tools/relation_anchored_train.py` and the shared `TrainingEngine`. Case code owns native sampling, physical transforms, loss terms and metrics; the shared core and its joint field prediction are unchanged. These recipes describe execution settings, not evidence of model convergence or permission to start a run.

## Recipes and entry point

Thermal recipes `configs/research/thermal_r15_2_joint_train{150,600}_v1.json` select direct joint prediction, while `thermal_r15_2_localports_train{150,600}_v1.json` enable the case-owned port head. The declared segmented schedule horizon is 200 epochs and the formal horizon is 500; both initially stop at 100. Wind recipes `configs/research/wind_relation_anchored_r15_2_w{0,1}.json` select `4x4x4` and `8x4x2` E grids respectively, with a 200-epoch schedule and an initial stop at 100. Configure the selected measured tile and physical microbatch before starting a lineage; retain its recipe and effective batch during resume.

From the repository root, replace the placeholders with the selected recipe and authorized run directory:

```sh
python tools/relation_anchored_train.py inspect --recipe RECIPE.json --device cpu
python tools/relation_anchored_train.py fit --recipe RECIPE.json --device cuda:0 --output RUN --stop-after 100
python tools/relation_anchored_train.py fit --recipe RECIPE.json --device cuda:0 --output RUN --resume latest --stop-after 200
python tools/relation_anchored_train.py evaluate --recipe RECIPE.json --device cuda:0 --output RUN --checkpoint latest
```

An extension requires its own authorization; the example does not authorize it. Resume uses the same recipe and run's latest state, with strict model and optimizer-group loading and restoration of provider state, RNG, sampler and history. A saved 500-epoch schedule can resume to an authorized later stop without resetting that schedule. An epoch visits the declared training membership once. `case_epoch_v1` keys native queries by dataset membership, epoch, physical case and role, rather than arm or microbatch position. Record actual GPU identity and ownership under the project instructions before execution.

The declared ordinary validation cadence is every 100 epochs; the engine also validates at a requested stop or clean stop. Latest state is saved every epoch, with 100-epoch milestones and a best-native-field selector. Curves first appear after the first completed epoch, refresh every 10 epochs and at a stop, and include weighted total TRAIN and validation losses plus components. Before the first validation the validation panel is marked pending. Progress is enabled by default and can be disabled in the recipe for unattended consumers. Totals use different TRAIN and validation reductions and need their prediction paths and term coverage read alongside them.

## Thermal objective and local readouts

Thermal preserves the native 16-angle, stride-4 field sampler and averages the full and restricted organized native losses during training. The port candidate adds equally weighted normalized outside-temperature and h losses on restricted 64-angle reads from the same prepared organization. The TRAIN-only channel scales, valid-port masks and per-channel valid-case reductions are saved in provider identity and loss metadata. Validation uses the restricted native prediction and restricted port read. The best-field selector uses native field accuracy rather than the augmented loss total.

Port targets are supervision and do not enter the scene or prescribed controls. The head consumes the organized outside prediction, angular geometry and prescribed heat/material properties. The h target is the saved epsilon-regularized, clipped effective coefficient with its validity mask; the nonnegative head does not add an upper bound because the packed metadata does not establish its numerical clip limit. These quantities do not constitute independently measured convection physics.

The local readout loads the declared epoch-4975 asset strictly with its own embedded transforms and frozen weights. It derives all four h/temperature summaries from the selected ports and evaluates present modules in one batched call. The case helper `channelthermal.local_ports_evaluation.evaluate_local_port_readouts` compares direct prediction with predicted-port, oracle-port and TRAIN-mean-h local readouts on the same batch; oracle ports use solved targets and are diagnostic only. Oracle scoring requires a complete valid 64-port sequence per module; the additional oracle-eligible comparison scores all four readouts on common physical and finite support, separately from full deployment metrics. The mean-h diagnostic uses raw organized outside temperature before the head residual and TRAIN-mean h, so it changes both inputs relative to predicted ports and does not isolate the h head. The CLI `evaluate` command reports native validation and port-loss metrics; call the case helper explicitly for the matched local-readout comparison. A terminal local result does not by itself establish a seamless coupled field or inverse readiness.

For a headless T0 checkpoint, strictly load the model first and prepare its native organization once. Use `channelthermal.local_ports.organized_outside64(model, prepared)` to obtain its restricted 64-angle outside temperatures, then call `ThermalCalibratedPorts(train_mean_h)(outside, prescribed, prepared.source_present)` and pass those ports with the original structure, heat and local query points to `FrozenThermalLocal`. Supply `train_mean_h` from the selected TRAIN membership only. The calibrated port constructor has no trainable parameters; the frozen local operator derives its summaries from those ports and uses the prescribed heat and material parameters. This terminal path uses no target ports, local feedback or fitted port head.

## Task-trained frozen Thermal local operator

The separate `thermal_r15_2_h_frozen_train150_v1.json` recipe transfers the direct T0 TRAIN150 epoch-100 weights and TRAIN150 transforms, then trains only a new temperature-condition head for 50 epochs. `thermal_r15_2_h_joint_train150_v1.json` is a conditional, separately named 50-epoch child of that phase-end checkpoint with a fresh optimizer and trainable global model/head. Their existence does not authorize either experiment. Historical port heads, checkpoint loading and exact-run resume remain unchanged.

The case-owned head receives actual restricted post-routing `context_M` and `context_E`, the joint physical [u,v,p,T] read, prescribed geometry/material/heat and angular coordinates. These contexts are weighted reductions of selected original members, not new physical groups. Trace requests are sliced within the saved query tile; physical conversion precedes native interpolation. Frozen-phase features retain no core gradient and are recomputed without a cache; the joint phase retains their live gradients. Work counters include the extra restricted decode and the single batched local call over present modules.

The h condition is prescribed harmonic interface conductivity divided by the native outside offset, rather than inferred from solved flux or temperature. The strict frozen epoch-4975 local operator derives its input summaries from the deployed ports and preserves gradients of those inputs. Its material, surface and flux-proxy losses reuse native masks, TRAIN scales, active-module means and case reductions. H-Frozen minimizes their equal mean plus 0.1 times outside-temperature loss. H-Joint adds 0.1 times that local mean and 0.01 times outside-temperature loss to the existing paired native objective. These starting weights are recorded experimental choices.

For these two recipes the validation field score and best-field selector use direct fluid predictions with local material/interface predictions. Report direct-global drift separately. Curves retain total TRAIN/validation objectives with distinct local and direct terms; ordinary validation remains every 100 epochs and at the 50-epoch phase stop. Compare the initial head, fitted head, raw-temperature/mean-h control and exposed oracle on identical receivers. A useful local fit does not establish physically correct boundary conditions, two-way coupling or conservation.

## Wind objective and cost

The Wind bridge uses the fixed TRAIN72/DEV24 layout-group membership, saved TRAIN-only normalizer and background profile, and the five-role objective: volume, hub slab, downstream envelope, near turbine and background, each with weight 0.2 and the existing per-component role scales. It predicts the three velocity components jointly. The two E64 grids retain the same physical support and represented volume. Ragged scenes are packed into one preparation/decode per microbatch with masked module padding and original IDs; work reports include the padding slots and actual core operations. Output and gradient parity with sequential execution is tested, while throughput and memory must be measured on the actual workload.

The optional W2 and W3 recipes use `8x4x4` E128 and `8x8x4` E256 respectively. They retain W0's four vertical levels, the same physical support and total represented volume, with per-record measures and axis lengths recomputed from the grid shape. W2 refines x; W3 additionally refines y. Each also changes address count and capacity, so this sequence is neither a pure count comparison nor a factorial resolution study. Fixed-weight cross-grid replay measures distribution sensitivity, while trained comparisons require matched epoch endpoints and unchanged objective scales.

An explicit existing role-scale calibration may be used when the file-based dataset fingerprint differs only after the saved and current non-fingerprint recipe bindings agree and the current deterministic 12-row TRAIN calibration panel reproduces every nonvolatile saved calibration field. The provider records both fingerprints and the panel-only scope. This replay verifies those calibration observations; it does not establish identity of the complete native dataset or authorize access to locked TEST data. The normal read-only loader remains strict for other workflows.

For execution comparisons preserve initial state, native rows, queries, objective, precision and effective batch. Measure complete preparation, prediction, loss and backward time and peak allocated/reserved memory; report preparation and decode work counters separately. Query tiles and microbatch packing can change numerical reduction order, so compare outputs, losses and gradients with appropriate numerical tolerances. Report actual executed member reads and pair calculations separately from memory or wall time; none alone establishes end-to-end speedup or physical causality.

## Fresh full-data 1000-epoch candidates

`thermal_r15_2_h_joint_train600_full1000_v1.json` initializes the joint relation-anchored global model and rich local-condition head from scratch, fits transforms/statistics on canonical TRAIN600, and monitors canonical VAL89. It uses the joint local-expert objective above from its first epoch, with the strict epoch-4975 local operator fixed throughout. It does not transfer subset-trained global/head weights or perform an automatic frozen-head warmup. The existing TRAIN150 transfer recipes retain their strict historical semantics.

`wind_relation_anchored_r15_2_w2_train420_full1000_v1.json` uses W2 E8×4×4 with the original TRAIN420 / VALID90 membership and locked TEST90. The full-TRAIN normalizer/background and five-role scales use the historical TRAIN-only recipes; the profile/normalizer replay covers all 420 rows with 8192 sampled volume receivers each, and role-scale replay retains its historical 12-row TRAIN panel. An explicitly named moved transform cache is reused only after exact numerical replay and membership/recipe checks, with old/current filesystem fingerprints recorded separately. No new cache store or dataset copy is created. The shared read-only catalogue has the historical full-data 128 GiB RAM ceiling.

Both candidates use fresh AdamW, constant learning rate 0.0003, their historical objective/sampling settings and FP32. Thermal retains Q1024/effective48/micro24 and Wind Q4096/effective24/micro4. Query tiles are selected by actual complete forward/loss/backward measurements on ordinary and largest-input-member microbatches before launch, while checking output/loss/gradient parity. The selected tile is saved in the run recipe and remains part of strict resume identity.

The full-data recipes stop at 1000 epochs, validate every 100 epochs, refresh loss curves every 10, save latest each epoch, and retain best-field plus each 100-epoch checkpoint. A user-authorized startup-only launch may end after successful startup verification without attaching a monitor or waiting for completion; ordinary in-process histories, validation, curves and checkpoints continue normally.
